## Skills

### ENCODE · [`encoding-hero-video-for-mobile`](skills/encoding-hero-video-for-mobile)

**問題** — ノート PC では完璧なヒーロー動画がスマホでは止まる：1792×3184、CRF 20 で 11.7 Mbps / 69 MB。約 7.5 Mbps のスマホ回線では 1 秒再生して 1 秒バッファ。

**使いどころ** — スマホ向けの 9:16 背景／ヒーロー動画すべて。すでにカクつく動画も。

**やること** — コマンド 1 つ。マスターが基準内（H.264、1440×2560 以下、6 Mbps 以下）なら remux のみ。それ以外は 1440×2560、CRF 23、preset slow、音声コピー。秒間ビットレートと `PASS` または `FAIL: rerun with 1920` を出力。

**なぜ CRF 23 か** — CRF が固定するのは知覚品質でビットレートではない：CRF 20 は静かなショットで 6 Mbps、動きの多い素材で 8.6 — そして 8.6 は止まる。CRF 23 は 5.7 に収まり、スマホサイズの背景では区別がつかない。1440×2560 超は残さない。スマホ画面の最大は 1290×2796。

**効果** — 69 MB → 34.5 MB、11.7 → 5.7 Mbps、次の動画を先読みしながら Fast 4G で最後まで再生。

### VERIFY · [`verifying-hero-video-on-mobile`](skills/verifying-hero-video-on-mobile)

**問題** — スマホで止まったヒーロー動画。*飢餓*（帯域超過のビットレート）か*ブロック*（自動再生ポリシー、低電力モード、古いタブ）か見分けがつかない。デスクトップ Chrome で再生できても証拠にならない。

**ENCODE との違い** — ファイルに触れない。ENCODE が動画を作り、VERIFY は「ページはスマホでそれを再生するか、しないなら理由は」に答える。独立して使える。

**使いどころ** — 任意。Tier 0 は常に（1 分）。Tier 1 はカクつきの報告や実機なしの出荷前証拠に。Tier 2 は「自動再生しない」「再生ボタン」のとき — 最初の一手はタブを閉じて開き直してもらうこと。

**やること** — Tier 0：ビットレート上限、`curl --limit-rate`、ETag = MD5 と先頭 1.5 MB の faststart、アップロード後に push、CDN の range キャッシュの罠。Tier 1：Chrome DevTools スロットリング、`Math.random` でクリップを強制選択。Tier 2：iOS シミュレータのコールドロードとアプリ切替の差分。

**効果** — ページのバグと端末状態を約 5 分で証拠付きで切り分ける。

### STITCH · [`video-clip-stitching`](skills/video-clip-stitching)

**問題** — 連鎖生成 — テイク N の最終フレームがテイク N+1 の先頭フレームになる — は、続きの各テイクの頭に約 0.5 秒のほぼ静止した「よどみ」を残す。素の `concat` は「止まった」「繰り返した」と見える。フレームは重複せず、動きが途切れる。コンテナのフレームレートも嘘をつく。

**使いどころ** — Dreamina、Runway、Higgsfield、Seedance などの 01 / 02 / 03 シリーズ。「止まる／繰り返す／滑らかでない／重なる」という苦情。生成素材の QC。

**やること** — `clip_qc.py` は 3 種のフレームレートを報告し、位相構造で水増しフレーム（7.5× vs 本物 1.1×）、停滞フレーム、プレビュー版の混入を検出。`seam_probe.py` はつなぎ目を分類 — 別ショット → ハードカット、構図の連続 → よどみを切ってディゾルブ、真の重複 → 再演部分を切る。`join_clips.sh` は 1 パスで、`xfade` の offset を計算し、ffmpeg の 3 つの地雷を除去。

**なぜ比率か** — カット点は「つなぎ目後の動き ÷ 前の動き」が 1.0 に近づく所（0.75 未満はよどみ、1.4 超はつんのめり）。曲線だけ見て 54 フレームと言ったことがあるが、正解は 0 だった。

**効果** — 再生に耐えるつなぎ目 — 下の比較を参照。

## つなぎ合わせのビフォー／アフター

<p align="center"><img src="assets/video-clip-stitching-seam-before-after-raw-join-vs-cut-30-frames.jpg" alt="猫のモバイル版クリップの 02→03 のつなぎ目：素の結合と最終カットを各 6 コマ・1 秒分、下にフレームごとの動き曲線" width="960"></p>

同じ素材、同じつなぎ目、それぞれ 1 秒。**上段 — 素の結合：** テイク 02 の最終フレーム、続いてテイク 03 の +0.00、+0.25、+0.50、+0.75、+1.00 秒。虹色の星は +0.50 秒でもまだ全開で、その後にようやく畳まれ始める。重複フレームはない — 動きが 0.5 秒止まるだけで、目にはそれが「止まった」「繰り返した」と映る。**下段 — 最終カット：** テイク 03 の先頭 30 フレームを除き、つなぎ目に 0.1 秒のディゾルブ。つなぎ目を過ぎた瞬間に畳まれ始め、+1.00 秒には舟がもう水面から浮いている。

**曲線**はフレームごとの動き（平均絶対差、5 フレーム移動平均）で、つなぎ目の 1 秒前から 2 秒後まで。つなぎ目の前は 2 本とも同じ素材。後では、素の結合は網掛けの帯に落ち込み — 0.5 秒間、直前のおよそ半分の動き（比 0.54）— 最終カットはすぐに立ち上がる（比 1.45）。この「後 ÷ 前が 1 に近づく」比率が、`seam_probe.py` がカット点を選ぶルール。

## STITCH · [`video-clip-stitching`](skills/video-clip-stitching)

**きっかけ** — 2026-09-01 の夜。依頼はほぼ原文どおり：「Downloads に cat mobile 01、02、03 がある。03 の最初の数フレームが 02 の末尾と重なって見える。編集でどう扱うか見て、最後に 1-2-3 をつないで 1 本にして。」14 分後に完成ファイルが戻り、返事は「え、ffmpeg でできると思ってたけど？…見てみたら、けっこういいじゃん」。エディタは一切使わず、すべて ffmpeg。その驚きがこのスキルの存在理由で、次の一言は「これ、スキルにできる？」でした。

**本当の問題** — 重なりではない。テイク 02 は紙の舟が六角の虹色の星に開いて終わり、テイク 03 は星が舟に折りたたまれて浮き上がるところから始まる。その間、03 の最初の 0.5 秒はほとんど動かない — 連鎖生成は参照フレームからゆっくり起動する。つまり、星が開ききって、0.5 秒止まり、それから畳まれる。その停止が「止まった」「繰り返した」と見える。フレームは 1 枚も重複していない、動きが途切れている。30 フレーム切ると、つなぎ目の動き比は 0.54 → 1.35 に。質感は完全には一致しないので 0.1 秒のディゾルブも添えた。

**次にフレームレート騒動** — 「元は 60 fps だったはず — なぜ出力が 30 に？」実際は違った。CapCut が自分の 30 fps プロジェクトタイムラインを表示していただけ。実測：2,789 フレーム中、重複は 2。しかし計測で本当の問題が 2 つ見つかった — テイク 02 は 13.4 % が停滞フレーム（生成の欠陥で、変換ではない）、Downloads の desktop 03 は 854×480 / 24 fps のプレビュー版で HD 版ではなかった。だから `clip_qc.py` は 3 種のフレームレートを報告し、位相構造で水増しを検出する（水増し素材は奇偶位相差 7.5×、本物は 1.1×）。

**そして 54 フレームの誤り** — 横版のバッチは見た目が同じだった。動きの曲線は 54 フレーム切れと言った。正解は 0 — 前のテイクがもともとゆっくり終わっていたので、つなぎ目の低い動きは一致していた。同じ曲線でも基準線が違えば結論は逆。残ったルールは、つなぎ目後の動き ÷ 前の動きが 1.0 に近づくこと（0.75 未満はよどみ、1.4 超はつんのめり）。

**今やること** — `clip_qc.py` で素材 QC、`seam_probe.py` で各つなぎ目を分類 — 別ショット → ハードカット、構図の連続 → よどみを切ってディゾルブ、真の重複 → 再演部分を切る — `join_clips.sh` で 1 パスエンコード、`xfade` の offset は手入力ではなく計算、ffmpeg の 3 つの地雷は事前に除去。最後に正直な受け入れ：尺の照合、つなぎ目のフレーム抜き出し、区間ごとの `volumedetect`。

**効果** — 再生に耐えるつなぎ目を持つ 2 本の完成カット（縦 46.5 秒、横 45 秒）と、何を再生成すべきかのリスト — 人が本当に必要とするのはそこ。

### ENCODE · [`encoding-hero-video-for-mobile`](skills/encoding-hero-video-for-mobile)

**きっかけ** — つないだ猫の動画 — 1792×3184、19 Mbps、112 MB — は翌日そのままサイトのモバイルローテーションに入った。追加したコミットには、解像度の基準は下限だから「縮小せず」ネイティブサイズを保った、と書いてある。CRF 20 で 11.7 Mbps / 69 MB。ノート PC では見事だった。

**翌朝** — 「前はスマホで自動再生していた。今は止まったまま。こちら側の問題か、自分のスマホの問題か？」Chrome の「Fast 4G」スロットルは実測約 7.5 Mbps。この動画は 1 秒再生、1 秒バッファ、9.16 秒でフリーズ。他の 3 本（5.4–6.6 Mbps）は同じ回線で最後まで滑らかに再生された。

**なぜ CRF 23 か** — モバイル標準の 1440×2560 に縮小しても CRF 20 では 8.6 Mbps — 39 秒で 5 回止まる。CRF が固定するのは知覚品質でビットレートではない：同じ CRF 20 でも静かなショットは 6 Mbps、猫と舟が通りを横切れば 8.6。CRF 23 は 5.7 Mbps で、次の動画を先読みしながら最後まで再生できた。スマホサイズの背景では 23 と 20 の区別はつかない。（同日午後：「CRF 23 のほうが 20 より*良い*んだよね？」— いいえ。低いほど高品質。23 はパイプを通る方。）1440×2560 を超えるものは残さない：スマホ画面の最大は 1290×2796、余分な画素は余分なビットレートでしかない。

**「じゃあ全部再エンコード？」** — それが次の質問 —「…いや待って、再エンコードするのはそっちだよね？」ファイルは 1 つ、しかももう済んでいた。このやりとりがそのまま製品仕様：コマンド 1 つ、判断は不要。

**やること** — マスターがすでに H.264、1440×2560 以下、6 Mbps 以下なら remux のみ（moov を先頭へ、世代劣化ゼロ）。それ以外は 1440×2560、CRF 23、preset slow、音声はコピー。最後に秒間ビットレート — 平均、p95、ピーク — と `PASS` または `FAIL: rerun with 1920`。

**効果** — 69 MB → 34.5 MB、11.7 → 5.7 Mbps、46 秒の動画がスマホで最後まで再生される。

### STITCH · [`video-clip-stitching`](skills/video-clip-stitching)

**解決する問題** — 連鎖生成 — テイク N の最終フレームをテイク N+1 の先頭フレームに渡す — では、続きの各テイクの頭に約 0.5 秒のほぼ静止した「よどみ」が残る。素の `concat` では「止まった」「繰り返した」と見える。フレームは重複していない、動きが途切れている。加えてコンテナのフレームレートは嘘をつく：30 fps の内容を 60 fps で包むと、どのヘッダーも 60 と言う。

**使いどころ** — Dreamina、Runway、Higgsfield、Seedance などの 01 / 02 / 03 シリーズ。「止まる」「繰り返す」「滑らかでない」「重なる」という苦情。生成素材をどこかへ出す前の QC。

**やること** — `clip_qc.py` は 3 種のフレームレート（コンテナ、フレーム密度、実効）を報告し、位相構造で水増しフレームを検出 — 水増し素材は奇偶位相差 7.5×、本物は 1.1× — さらに停滞フレーム比率とプレビュー版の混入も。`seam_probe.py` は各つなぎ目を処理が正反対の 3 種に分類：別ショット → ハードカット、構図の連続 → よどみを切ってディゾルブ、真の重複 → 再演部分を切る。カット点は「つなぎ目後の動き ÷ 前の動き」が 1.0 に近づく値。`join_clips.sh` は 1 パスでエンコードし、`xfade` の offset は手入力ではなく計算、ffmpeg の 3 つの地雷は事前に除去。

**なぜ比率なのか** — 曲線だけを見て 54 フレーム切ると判断したことがあるが、正解は 0 だった — 前のテイクがもともとゆっくり終わっていたので、低い動きは一致していた。同じ曲線でも基準線が違えば結論は逆。見た目が同じ 2 バッチで 30 と 0。

**効果** — 再生に耐えるつなぎ目と、正直な受け入れ手順：尺の照合、つなぎ目のフレーム抜き出し、区間ごとの `volumedetect`。

## これらはどうやって生まれたか

どれも計画したものではない。サイトのヒーロー動画は、猫が夜の街で光る紙の舟を追いかける映像で、3 テイクに分けて生成し、各テイクは前のテイクの最終フレームから始めた。2 晩で、その 1 本の素材から 3 つのスキルが順に生まれた。

**STITCH、2026-09-01 の夜。** 依頼はほぼ「Downloads に cat mobile 01、02、03 がある。03 の最初の数フレームが 02 の末尾と重なって見える。どう扱うか見て、最後に 1-2-3 をつないで 1 本に」。14 分後に完成ファイルが戻り、返事は「え、ffmpeg でできると思ってたけど？…見てみたら、けっこういいじゃん」。すべて ffmpeg だった。次の質問は、これをスキルにできるか。途中には：フレームレート騒動（「元は 60 だったはず — なぜ 30 に？」— CapCut が自分の 30 fps タイムラインを表示していただけで、ファイルは本物の 60）、テイク 02 に 13.4 % の停滞フレーム、Downloads の desktop 03 が 854×480 のプレビュー版だったこと、そして自信満々に「54 フレーム切る」と言って正解が 0 だったこと。

**ENCODE、翌日。** つないだ動画 — 1792×3184、19 Mbps — がネイティブサイズのままサイトのモバイルローテーションに入った。コミットは解像度基準を下限と書いていた。CRF 20 で 11.7 Mbps / 69 MB。翌朝：「前はスマホで自動再生していた。今は止まったまま。こちらの問題か、自分のスマホの問題か？」原因が分かった後：「じゃあ全部再エンコード？…いや待って、再エンコードするのはそっちだよね？」ファイルは 1 つ。このやりとりが仕様：コマンド 1 つ、判断なし。

**VERIFY、同じ朝。** 修正は 04:47 に本番へ。その後：「まだ自動再生しない」—「再生ボタンが見える」—「モバイルの Chrome アプリ」—「Safari は問題ない」—「Chrome は再生を押しても反応なし…」—「気にしないで」—「急に直った」。20 分。バグは昨日のページを動かし続けていた Chrome のタブ。その間に iOS シミュレータはサイトをコールドロードし、アプリを切り替えて戻り、自動再生も再開もすることを証明していた。壊れていない visibility ロジックを「修正」した人はおらず、チェックリストに最も役立つ 2 行が入った：まずタブを閉じて開き直してもらう、本番の動画を同名で上書きしない。
